# whb-cross-section-load

Cloudflare Worker: принимает входящий вебхук от Planfix `{fileUrl, apiKey}`, скачивает файл заявки
(бланк заказа, лист «Заявка»), сопоставляет позиции со справочниками Planfix
**Типы изделий** (7084) и **Сечения изделий** (7082), и возвращает распознанные позиции
прямо в ответе на этот же запрос — без отдельного обратного вебхука, обработка достаточно
быстрая, чтобы Planfix мог тут же разобрать ответ и добавить аналитику «Изделия РД».

## Установка

```bash
npm install
npx wrangler secret put PLANFIX_TOKEN   # Bearer-токен Planfix REST (whb.planfix.ru)
```

Для локальной разработки — положить тот же токен в `.dev.vars` (не коммитится):

```
PLANFIX_TOKEN=...
```

## Разработка

```bash
npm run dev   # wrangler dev --config ./wrangler.toml, http://localhost:8787
```

**Важно:** в `~/Downloads` лежит чужой `wrangler.jsonc` (от другого проекта, seppra-dashboard) —
wrangler может подхватить его вместо локального `wrangler.toml`, если запускать без явного
`--config ./wrangler.toml`. Все npm-скрипты (`dev`/`deploy`/`tail`) уже используют
`wrangler` без явного конфига, поэтому запускать их нужно из этой директории или добавить
`--config` вручную, если возникнет ошибка «entry-point file... was not found».

## Деплой

```bash
npm run deploy
```

## Вход (POST /)

Реальный вид (из Planfix, макрос ссылки на файл актуального расчёта):

```json
{
  "fileUrl": {{Задача.Надзадача.Сделка / Актуальный расчёт.Файлы.Ссылка}},
  "apiKey": "05e15d8cba3eb5ce6ef3a7529516916e"
}
```

Алиасы ключей (сопоставление регистронезависимое):
- `fileUrl` / `url` / `file` / `link` / `fileLink` — обязателен
- `apiKey` / `key` / `token` / `planfixToken` — Bearer-токен Planfix REST, используется и для
  чтения справочников 7084/7082, и (при 401/403) для скачивания файла. Необязателен в запросе —
  если не передан, берётся `env.PLANFIX_TOKEN` (секрет; только для локальной разработки).

`taskNo` и обратный вебхук/`callback` не нужны — Planfix и так знает текущую задачу (это её же
вебхук), а результат возвращается прямо в ответе на этот же запрос (обработка достаточно быстрая).

Файл скачивается сначала без авторизации (planfix filelink обычно уже содержит подписанный
`&auth=`), при 401/403 — повторно с заголовком `Authorization: Bearer <apiKey>`.

## Выход

```json
{
  "items": [
    { "type": "Подкладной брус", "section": "40х240 2с", "quantity": 150, "description": "" },
    { "type": "Балка стеновая", "section": "240х202 1с Цельный", "quantity": 9.405,
      "description": "Фундаментный венок: Rofalin Acryl - ???????, Грунтовка - Impragniergrund GN-15; Фундаментный" }
  ]
}
```

Один массив `items`, каждый элемент — `{type, section, quantity, description}`. `type`/`section` —
точные текстовые названия записей справочников (Planfix сопоставляет их по названию, не по id).
`unit` и метаданные (`matchedCount`/`skipped`/...) специально убраны из ответа — минимальная
структура по просьбе пользователя.

### Извлечение данных в настройках вебхука Planfix

Настроить извлечение из ОТВЕТА этого же вызова (не из отдельного вебхука). Один инфоблок
на весь массив, JSONPath `items`, сохранение «Все значения» — дальше в действии «Добавить
аналитику» ссылаться на под-поля `.type` / `.section` / `.quantity` / `.description` этого
инфоблока (так же, как раньше был устроен `cross-section`, только теперь один уровень, а не
плоский массив объектов на верхнем уровне):

| Название инфоблока | JSONPath | Сохранить    |
|---------------------|----------|--------------|
| items                | `items`  | Все значения |

Если Planfix не умеет доставать под-поля из инфоблока-массива объектов и нужны именно
**два отдельных инфоблока** (типы изделий и сечения изделий раздельно) — извлекайте их прямо
из массива `items` через JSONPath с указанием ключа внутри каждого элемента:

| Название инфоблока | JSONPath      | Сохранить    |
|---------------------|---------------|--------------|
| type (типы изделий)  | `items[*].type`    | Все значения |
| cross-section (сечения изделий) | `items[*].section` | Все значения |

Оба выражения возвращают массив значений в том же порядке, что и `items` — i-й элемент
`type` соответствует i-му элементу `cross-section` (та же строка заявки). Если Planfix не
поддерживает синтаксис `[*]`, альтернативная запись — `items.*.type` / `$.items[*].type`
(зависит от диалекта JSONPath в конкретной версии Planfix — проверьте в самой форме
«Извлечение данных», какой вариант даёт непустой результат на тестовом вызове).

## Автосоздание типов изделий

Если позиции из Excel нет в `TYPE_MAP` (или там `null`) — берётся имя строго как в Excel,
и если такой записи ещё нет в справочнике «Типы изделий» (7084), Worker создаёт её
автоматически через `POST /directory/7084/entry/` (нужен токен со scope на создание записей
справочника). Повторные строки с тем же именем в одном файле не создают дублей — сначала
проверяется уже загрученный список типов (и то, что Worker сам создал парой строк выше).

**Сечения (7082) НЕ создаются автоматически** — там неоднозначность по полю «Вид»
(Цельный/Комбинированный/Пустотелый), это осознанное решение, не угадывание.

## Известные пропуски

- Сечения, которых нет в справочнике 7082 при заданном сорте (напр. Стропила 152×246 2с),
  или где несколько вариантов «Вида» и непонятно, какой нужен.
- Позиции с нестандартным форматом сечения («Накладки нижние» — «на 240» вместо A×B) и раздел
  «Окна и двери» — не парсятся вовсе (другая структура таблицы).
- «Карнизная и лобовая планка» — в справочнике 7084 есть 3 отдельных профиля (нижний/средний/
  торцевой), а в Excel все 3 строки называются одинаково; автосоздание в этом случае создаст
  (или найдёт) ОДНУ общую запись «Карнизная и лобовая планка» для всех трёх — если нужна
  разбивка по профилю, потребуется отдельное правило сопоставления.

Список исходных соответствий — таблица `TYPE_MAP` в `src/index.js` (скопирована 1:1 из
прототипа [`whb-zayavka-rd/zayavka_rd.html`](../../whb-zayavka-rd/zayavka_rd.html)).
